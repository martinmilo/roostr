## The problem this record serves

farmr will run roostr in every service container and expose it through its own MCP server
and TUI. An "hq" agent reads each service's map to decide which services a task touches and
briefs per-service agents; farmr's TUI shows each container's check result. Parsing
roostr's screens would be fragile: lines wrap, columns move, sections are left out when
empty. Re-implementing roostr's rules in farmr (what counts as described, what needs
attention, what check reports) would drift. So: a stable, versioned JSON contract.

The precedent that holds up is Terraform's `format_version`: additive changes keep the
version, consumers ignore keys they do not know, and a breaking change bumps it.

## Decided

### Which commands, and where `--json` goes

- `--json` on the five read commands: the overview (`roostr --json`), `show <id>`,
  `changes`, `validate` and `check`.
- Not on `scan` or `init`: there it is an option the command does not take, exit 2 naming
  it, as for any unknown option.
- `--json` may stand anywhere among the arguments: `roostr --json show book-workshop`,
  `roostr show --json book-workshop` and `roostr show book-workshop --json` are the same.
  It combines with the command's options: `changes --since 7d --json`,
  `check --json --base HEAD`.
- **Proposed**: `--json` is never read as the value of another option, nor as a command's
  argument. `--since --json` is `--since` with no value; `show --json` is `show` without
  an id, exit 2, where a parser that takes "the next argument" would look for a process
  called `--json` and exit 1. Only the second is observable by exit code, so only it has a
  test (197a); `--since --json` exits 2 either way.

### The contract

- stdout carries exactly one JSON object, in UTF-8, and nothing else. Whitespace, key order
  and the escaping of characters are free; the tests parse the output and never compare
  bytes.
- Every object has `"format": 1` at the top level. Adding a key keeps the format; removing
  a key or changing what one means bumps it; consumers ignore keys they do not know.
  **Proposed** while writing FORMATS.md: a new `kind` of check problem also keeps the
  format, and a consumer treats a kind it does not know as a problem. Without that, every
  new check would break farmr's gate.
- Exit codes are unchanged. Exit 2, and `show`'s exit 1 for an id that does not exist,
  print nothing on stdout and give the reason as text on stderr, as today. `validate` and
  `check` with findings exit 1 *with* their JSON on stdout.
- An optional value that is absent is still there: `null` for a single value, `[]` for a
  list. A consumer never tests whether a key exists.
- `null` where the text says something was not compared or not scanned, or roostr could
  not tell: `entrypoints` of the overview without `entrypoints.tsv`, `entrypoints` of
  `changes` when not compared, `needs_attention` of the overview outside Git. An empty list
  is a count of zero, `null` is "not known". This is the house rule "absence is never shown
  as zero" (record 1), carried into JSON.
- Order follows the text output: processes by id; operations, environments, outcomes and
  files in file order; entrypoints in `entrypoints.tsv` order; check's problems in block
  order, then in item order.
- An entrypoint is referred to by the `<kind> <name>` string records use.
- **Proposed**: a value is the string YAML reads, unchanged. A `try` written as a `|`
  block ends in the newline that YAML keeps; a `checked` date is the string `2026-10-08`;
  quotes, backslashes, tabs, accented letters and emoji come back as written.
- Keys are written in snake_case, as the YAML keys are (`watch_out`).

### Shapes

FORMATS.md, "JSON output", has every shape as a key table and is the contract farmr builds
on. In short:

`<process>`, the same in the overview and in `show`:

```
{ "id", "name", "description", "group": string|null,
  "entrypoints": ["<kind> <name>", ...],
  "files": [{"path", "note": string|null}],
  "try": string|null,
  "outcomes": [{"name", "when", "then"}],
  "why": [string, ...],
  "checked": "YYYY-MM-DD"|null }
```

**The overview, `roostr --json`:**

```
{ "format": 1,
  "project": { "name", "stack": string|null, "description": string|null,
               "watch_out": [string, ...],
               "operations": [{"name", "command", "note": string|null}],
               "environments": [{"name", "where"}] },
  "processes": [<process>, ...],
  "entrypoints": null | { "covers": [kind, ...],
                          "rows": [{"entrypoint", "kind", "name", "file",
                                    "area": string|null, "processes": [id, ...]}] },
  "needs_attention": null | [{"process": id, "files": [path, ...]}],
  "needs_checking": [{"file": path}] }
```

- `processes`: every readable record (below), by id.
- `entrypoints.covers`: the kinds of the `# covers:` line, in the closed list's order.
  `rows`: the rows the overview counts, in `entrypoints.tsv` order; `processes` gives the
  ids of the records that list the row, by id, `[]` for none. "8 entrypoints, 5 described",
  the areas and their counts, `none found` and `not scanned` all follow from these.
- **Proposed**: each row also carries `entrypoint`, its `<kind> <name>`, so a consumer
  matches a row to `<process>.entrypoints` without rebuilding the string.
- `needs_attention`: the processes NEEDS ATTENTION names, by id, each with its files in the
  order of the record's `files`. `null` when roostr cannot tell (decided after review, 1).
- `needs_checking`: the files NEEDS ATTENTION says need checking, in the order of their
  paths, which is the order the text lists them in today: `.roostr/entrypoints.tsv` before
  `.roostr/processes/...` (decided after review, 2).
- LAST 7 DAYS is not in it; `changes --json` has it.

**`roostr show <id> --json`:**

```
{ "format": 1, "process": <process>,
  "entrypoints": [{"entrypoint": "<kind> <name>", "file": path|null}] }
```

**Proposed**, the second key: the text of `show` gives each entrypoint's file from
`entrypoints.tsv` or says it is not there, and the JSON should not carry less than the
screen. `file` is `null` when the entrypoint is not in `entrypoints.tsv` (a row's file is
never empty, so `null` is unambiguous). One item per entrypoint the record lists, in its
order.

**`roostr changes --json`:**

```
{ "format": 1, "since": "YYYY-MM-DD",
  "entrypoints": null | {"added": [ref, ...], "removed": [ref, ...]},
  "processes": [{"id", "subjects": [string, ...]}] }
```

`entrypoints` is `null` where the count line says `not compared`. Added and removed are in
the file's sort order; processes by id; subjects newest first, as in the text.

**`roostr validate --json`:**

```
{ "format": 1, "problems": [<invalid>, ...] }
<invalid> = { "kind": "invalid", "file": path, "key": string|null, "line": number|null,
              "message": string }
```

validate's lines had three shapes (seen running the program):

```
.roostr/processes/refund-booking.yml: entrypoints.1: entrypoint http POST /refunds is not in entrypoints.tsv
.roostr/processes/cancel-booking.yml: cannot parse YAML: while parsing a flow sequence, ...
.roostr/entrypoints.tsv: line 9: unknown entrypoint kind "webhook"
```

and a fourth without a colon: `.roostr/entrypoints.tsv is missing; run roostr scan to check
process entrypoints`. Split, with a `line` the brief did not have (decided after review,
4): `file` always; `key` the dotted path when the finding is about a key, else `null`;
`line` the line of `entrypoints.tsv` when it is about a row, else `null`; `message` the
rest, validate's own wording, which is not part of the format. The text line is then
always `<file>: <key or "line <n>">: <message>`, or `<file>: <message>` without either,
which changes the wording of the one line without a colon to
`.roostr/entrypoints.tsv: ...` (233a). Splitting lets farmr group findings by file and
point at a key without parsing roostr's English.

**`roostr check --json`:**

```
{ "format": 1, "base": string|null, "problems": [<problem>, ...] }
```

`base` is the value given to `--base`, as written, or `null`. One problem per item of the
text output, each with `kind`:

| `kind` | Other keys | Text block |
|---|---|---|
| `invalid` | `file`, `key`, `line`, `message`: the same object `validate --json` gives | VALIDATE |
| `entrypoints_behind` | `added`, `removed`: lists of refs, possibly both empty | ENTRYPOINTS |
| `entrypoints_never_written` | none | ENTRYPOINTS |
| `scan_not_executable` | none | ENTRYPOINTS |
| `scan_failed` | `exit_code`: number; `stderr`: string, exactly what the script wrote | ENTRYPOINTS |
| `scan_malformed` | `reasons`: `[{"line": number, "message"}]` | ENTRYPOINTS |
| `needs_attention` | `process`: id; `files`: list of paths | PROCESSES |
| `not_described` | `entrypoint`: ref | NOT DESCRIBED |

- `needs_attention` is the same object as an item of the overview's `needs_attention`, with
  `kind` added; `invalid` the same object as `validate`'s.
- **Proposed**: `scan_malformed` reasons are split into `line` and `message`, as
  `invalid` is, since every reason `roostr scan` gives names its line (FORMATS.md).
- `stderr` of `scan_failed` is the whole of what the script wrote, several lines and the
  final newline included.
- Clean: `"problems": []`, exit 0. With `--base` and nothing changed after it, the same.
- The paragraphs of the text (what to do) are not in the JSON: they are wording, not
  contract. A consumer that wants them runs `roostr check` without `--json`.

### What "readable" means (**Proposed**, accepted; settles an open question of record 3)

The overview leaves out of FUNCTIONALITY, and lists under NEEDS ATTENTION as "needs
checking; run roostr validate", every record about whose own content validate has
something to say: it does not parse, is not a mapping, lacks `name` or `description`, has
an unknown key, a key of the wrong shape, an entrypoint of an unknown kind, an entrypoint
listed twice, or a `checked` that is not a date. A record whose findings are only about
other files (a listed file that does not exist, an entrypoint not in `entrypoints.tsv`) is
shown as usual. `show` refuses the first kind, exit 2. `entrypoints.tsv` with a row of an
unknown kind is listed the same way, and that row is not counted.

JSON makes the rule a contract, because `<process>` can only be filled from a record of
the right shapes (a `why` written as one string has no list to give). This record pins the
rule as the program already had it: a record is **readable** when `validate` reports
nothing about its own content. Record 3 left open "whether the overview should treat a
record with an unknown key as unreadable"; this closes it: yes, as a typo such as
`outcome:` would otherwise drop data silently.

So the overview's `needs_checking` and the VALIDATE block of check do not have the same
shape, nor the same members, and are not meant to: `needs_checking` lists files the
overview could not use, one entry per file; `invalid` lists findings, several per file,
and includes findings that leave a file usable.

## Decided after review

All four raised by this record, accepted by the coordinator for the owner as recommended.

1. **`needs_attention` is `null` when roostr cannot tell, `[]` when it can and nothing is
   behind.** The brief had `[]` outside Git. With `[]`, a consumer cannot tell "nothing
   needs attention" from "roostr could not tell", and the hq agent would read a project
   outside Git as up to date. In a repository with no commits yet it is `[]`: Git was read,
   and a record never committed is skipped by rule. FORMATS.md states the rule generally,
   "`null` when the project is not in a Git repository, or Git could not be read", because
   the next piece of work makes the overview keep working when Git is missing or refuses
   the repository (a slim container without git, Git's "dubious ownership"); there too it
   is `null`, and the contract need not change. Scenarios 217, 219 and 219a.
2. **`unreadable` renamed `needs_checking`, entries `{"file": path}`.** The overview's own
   words are "needs checking", and the list also holds `entrypoints.tsv` when a row has an
   unknown kind; that file is read (only the row is dropped), so "unreadable" would be
   wrong for it. Why a file needs checking is what `validate --json` says. Scenarios 216a,
   220, 220a.
3. **Length limits do not make `project.yml` unreadable**, in text or JSON. The program
   made the overview and `show` exit 2 on any `validate` finding about `project.yml`,
   including a long note ("Cannot read .roostr/project.yml: environments.staging: must have
   at most 160 characters"), while records 1b and 3a say "The overview prints whatever is
   there; only `validate` complains". No test pinned either. A farmr hq agent must not
   lose a service's whole map over one long note. Now: the limits (`watch_out` items and
   count, an operation's note, an environment's value) are reported by `validate` and
   `check` only; the overview prints the value whole; parse and shape errors still make
   the overview and `show` exit 2. Scenarios 223, 223a, 223b, 223c.
4. **Additions to the brief's shapes:** `line` in `invalid`; `entrypoint` on each row of
   the overview; `show`'s `entrypoints` with their files; `scan_malformed.reasons` as
   `{line, message}`; `--json` never another option's value. With the split of
   validate's line, the one line without a colon is reworded.

## Test kit

- `assert_json "process.files.2.note", nil`: the value at a dotted path of keys and
  positions counted from 1, as validate's paths are. A missing key fails, never passes as
  `nil`, so `null` and absent stay apart. `*` is every item of a list
  (`"processes.*.id"`). The expected value is compared with `===`, so a pattern matches a
  string and `String` matches any string. A failure shows the path, both values and, when
  a step is missing, the part that is there.
- `assert_json_is expected("show_book_workshop.json")`, or `at: "project"`: the parsed
  output equals the parsed file. A failure shows both indented, with the output's keys in
  the expected order, line by line as `assert_stdout_is` does.
- When stdout is one JSON object, a failure transcript shows it indented, up to 80 lines.
- Every command helper passes arguments on: `overview "--json"`, `validate "--json"`,
  `scan "--json"`, `init "--json"`.
