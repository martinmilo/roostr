# Record 12: fixes to the project map and to what text output prints

Date: 2026-11-06. Changes behaviour of records 1 to 11, which all stand except where this
record says otherwise. Branch `map-fixes`, from `session-work` (record 11, the worker's
record 11 build, 55b81b0, and the coordinator's README commit, 0bb9aa4).

Status: decided by the shaper on the coordinator's brief. A black-box QA round on the map
ran an independent oracle that matched the map byte for byte in more than 330 runs, and
found the eight problems below; the coordinator re-checked four of them on the record 11
build, and the shaper reproduced 1, 2, 3, 6, 7 and 8 on it as well. The coordinator gave a
lean for each and left the choice open; the choices and the reasons are here. The QA also
confirmed what needs no test: an empty or missing `processes/` folder, Latin-1 bytes,
symlinked, dangling, looping and unreadable records, and the variants of stdin.

Record 10's "Still open" had three of these: `show` and the overview printing invisible
characters as written (8), form (c) dropping a whole group line (2), and a long name (6).
This record closes all three.

## Decided

### 1. Operations that ship are left out of the map

Record 10 left out only an operation named exactly `deploy`, because agents use what they
are shown and a deploy is not theirs to run. `deploy-production: fly deploy --app
shop-prod`, `deploy:staging` and `release: bin/release production` reached the agent all
the same, and so did `de<U+00AD>ploy`, which the map prints as `deploy`.

**Decided:** the map leaves out an operation whose name, as the map prints it (after the
characters it removes), has `deploy`, `release` or `publish` as one of its words, in any
letter case. The words of a name are its runs of letters; every other character separates
them. So `deploy`, `Deploy`, `deploy-production`, `deploy:staging`, `staging.deploy`,
`release` and `publish_gem` are left out, and `deployment-status` and `predeploy-check`
stay.

Why a word anywhere, not only the first: `production-deploy` and `staging.deploy` ship as
surely as `deploy-production`, and a name like `release-notes` left out costs the agent one
hint; the overview still lists every operation. Why these three: they are the verbs that
reach a deployed system in Capistrano, Kamal, Fly, Heroku, npm and RubyGems. `rollback` was
considered and left out of the list: `db-rollback: bin/rails db:rollback` is a common local
operation. `ship` and `promote` are rarer, and a name made only of them stays.

### 2. Form (c) cuts ids, not whole lines

Form (c) removed whole lines from the end. 350 processes with no group and ids of 20
characters make one line `other: ...` longer than 8,000 bytes on its own: (c) dropped it,
left the legend `Process ids by group:` with nothing under it, and said "the last 1 lines"
(QA, `scratchpad/qa-m/gen.rb DIR n=350 groups=0 idlen=20 wo=0 ops=1`, 561 bytes and no
process).

**Decided:** form (c) cuts form (b) at its end one item at a time until it fits. The
process ids go first, from the last back: a group line that has lost some of its ids ends
in `, ...` after the last id it keeps; a group line with none left goes, and the legend
goes with the last one. Then operations go, from the last; then watch-out items, from the
last; then the Description line, then the Stack line. A heading with nothing under it goes,
with its blank line. The closing line says what was cut:

- while some id is left: `each process's description and files, and <n> of the <total>
  process ids`;
- once none is: `every process`, then `every operation` or `<n> of the <total>
  operations`, `every watch-out item` or `<n> of the <total> watch-out items`, `the
  Description line`, `the Stack line`, each when it was cut; separated by `, `, the last by
  `, and `.

Why counts per part instead of lines: a count of lines with blank lines and headings among
them told the agent little, and "1 lines" was wrong English. `<n> of the <total>` reads
right for every number; `every ...` is said when all of a part is gone. Why the Description
and Stack lines can go: the record 11 build already cut them as lines, and without that a
description of 8,000 bytes breaks the 8,000-byte promise as a long name does (6).

Form (b)'s notation in FORMATS, `<group>: <id>, <id>, ...`, used `...` for "and so on"; it
now says "every id of the group, separated by `, `", since `, ...` marks a cut.

### 3. A record whose file name holds a hidden character

`refund<U+202E>redro.yml` passed `validate`, and the map showed `refundredro`, an id
`roostr show` does not know. The same with ESC, a tab, a newline or a zero-width space.

**Decided:** `validate` reports a record's file name that holds a character the map removes
or changes: a control character (a tab and a line break among them), U+2028, U+2029, a
format character, a default-ignorable code point. The finding is about the whole file:
`<file>: the file's name holds U+202E, a character that is invisible or changes how text
shows: rename the file`, the characters named once each in order, as for a string. The map
leaves such a record out. The record stays readable (the finding is about its name, not its
content), so the overview lists it and `show` with its exact id prints it, each with the
characters written out (8).

Why the map's set, not `validate`'s narrower one: the point is that the map's id and the
file's id agree, so anything the map would drop or change is a problem in a file name, a
soft hyphen or a zero-width joiner too. Why left out of the map rather than shown escaped:
the map is for the agent, and an id it cannot use is noise; `validate` and the gates name
it. Why only these characters: ids with spaces or commas, or in NFD, are left out of this
record (below).

### 4. The flags of England, Scotland and Wales

They are U+1F3F4, then tag characters, then U+E007F, so `validate` reported them and every
gate blocked.

**Decided:** `validate` does not report the three flags Unicode recommends for general
interchange: U+1F3F4, the tag characters that spell `gbeng`, `gbsct` or `gbwls`, and
U+E007F (UTS #51, Annex C and ED-14a; the RGI tag sequences). Any other run of tag
characters is still reported, after U+1F3F4 too. The map still removes the tag characters,
so a flag is U+1F3F4 alone there.

Why only the three, not every well-formed tag sequence: UTS #51 allows a `tag_spec` of up
to 30 tag digits and lowercase letters after U+1F3F4. Allowing that form would let
`ignorepreviousinstructions` through, spelled in tags that do not show, which is the whole
reason tags are reported. Why the map still removes them (the lean was to keep them): the
map already turns 👩‍💻 into 👩💻 and ⚠️ into ⚠; one rule, everything default-ignorable
goes, is simpler, and a black flag loses little.

### 5. Characters that show as nothing outside Cf

U+3164, U+115F, U+1160 and U+FFA0 (Hangul fillers), U+17B4 and U+17B5 (Khmer inherent
vowels), U+034F and U+2800 passed both `validate` and the map.

**Decided, the map:** it removes every default-ignorable code point as well as the control
and format characters. FORMATS lists the property's ranges as of Unicode 18.0, taken from
DerivedCoreProperties-18.0.0.txt (fetched from unicode.org on 2026-11-06): U+00AD, U+034F,
U+061C, U+115F..1160, U+17B4..17B5, U+180B..180F, U+200B..200F, U+202A..202E,
U+2060..206F, U+3164, U+FE00..FE0F, U+FEFF, U+FFA0, U+FFF0..FFF8, U+1BCA0..1BCA3,
U+1D173..1D17A, U+E0000..E0FFF. Ruby 3.4's `\p{Default_Ignorable_Code_Point}` (Unicode
15.0) gives the same ranges. The file derives the property as
Other_Default_Ignorable_Code_Point + Cf + Variation_Selector, less White_Space,
U+FFF9..FFFB, U+13430..13440 and the prepended concatenation marks.

**Decided, `validate`:** it reports, beyond record 9's list, the Hangul fillers U+115F,
U+1160, U+3164 and U+FFA0, the Khmer vowels U+17B4 and U+17B5, and the default-ignorable
code points no character is assigned to: U+2065, U+FFF0 to U+FFF8, U+E0080 to U+E00FF and
U+E01F0 to U+E0FFF. So the lists now read `U+2060 to U+2065`, `U+FFF0 to U+FFFB`, and the
unassigned ranges beside the tags. It does not report U+034F (combining grapheme joiner,
used in Hebrew and to keep marks apart), U+180B to U+180D and U+180F (Mongolian variation
selectors), the rest of the format characters, or U+2800.

Why the unassigned ones, beyond the brief: they show as nothing by Unicode's own rule, no
text can hold them honestly, and they sit next to the tags; a hidden payload could use
them as well as the tags. Why not U+2800, the braille pattern blank (the brief said "if you
agree"; the shaper does not): it is not default-ignorable, it shows as a blank one
character wide, as U+3000 and the other spaces do, and it hides no text, since the other
255 braille patterns are visible dots. The map keeps it.

### 6. A very long project name

A name over about 7,700 bytes made the map exceed 8,000 bytes, since the header is never
cut.

**Decided:** in the map's header a name of more than 200 characters (code points, as the
map prints it) is cut to its first 200 and `...`. Nothing else in the header is cut, so the
header is at most about 1,100 bytes and (c) can always fit. The overview still prints the
name whole. Why 200: names are short; 200 keeps any real name whole, and the cut is about
the promise, not about style. A `validate` limit on `name` was considered and left out: it
would block every gate for a long name that hurts only the map.

### 7. Named pipes and devices

A named pipe `p.yml` in `.roostr/processes/`, or a symbolic link to `/dev/zero`, made
`session start` and `validate` wait or read forever, and `validate` runs in the pre-commit
hook. On the record 11 build a link to `/dev/zero` was killed by the kernel for its memory
within 20 seconds.

**Decided:** `project.yml`, `entrypoints.tsv` and every record are read only when they are
a regular file or a symbolic link to one. Anything else (a named pipe, a socket, a device,
a link to one) is never opened: `validate` reports `<file>: not a regular file; roostr
reads only regular files`, and every other command treats it as a file it cannot read (a
record left out and listed under NEEDS ATTENTION, a `project.yml` that stops the overview
and gives no map). A folder whose name ends in `.yml` is still a folder. The tests use a
named pipe and a link to `/dev/null`: a link to `/dev/zero` is the same case, and on a
build that reads it would eat memory until the kit stops it.

The record 11 snapshot was checked for the same trap: Git's status does not list named
pipes, and the snapshot notes an untracked symbolic link as a link, without reading it
(`app/zero.bin -> /dev/zero` gave a session record at once).

### 8. Control and bidi characters in text output

`validate` and `check` echoed keys and file names as written: a key `bell\a`, a key
holding U+202E, a file `bad\e[31mred.yml`. That garbles the terminal and the report the
Stop hook gives the agent. Record 10 left open whether the overview and `show` should do
anything about such characters in values.

**Decided:** every text output, of every command, on stdout and stderr, writes each
character `validate` reports as `<U+XXXX>` (four to six hexadecimal digits in capitals, the
names its findings use); in a file name, a path, a key and an id also a tab and a line
break. The overview and `show` do the same for values. JSON output gives every string as
it is, and the map removes these characters as before. What people write on purpose (a tab
in a value, ZWJ, the Hebrew and Arabic marks, the three flags) is printed as it is.

Why the overview and `show` too: an ESC sequence can do more than colour a terminal (OSC 52
writes the clipboard); a right-to-left override reorders what a person reads; and an agent
that runs `roostr show` would read tag characters it cannot see, the very thing the map
removes. Written out, each is harmless and shows the name its finding gives. Why not JSON:
it is for programs, and its consumers deserve the value as stored.

## For the worker

- Form (c)'s size only falls as ids are cut (an id and its `, ` are at least 3 bytes, and
  the count in the closing line grows by at most one digit), so a search over the number of
  ids cut gives the same map as cutting one at a time (record 11's C5).
- The default-ignorable ranges are listed in FORMATS; a Unicode table older than 18.0 may
  differ elsewhere, but not in this property since 15.0.

## After the worker's build (9c87552, 688 of 688)

- FORMATS said names write out only what `validate` reports in a string, plus a tab and a
  line break, while 574 expects `re<U+00AD>fund-booking.yml`. Settled as the worker read
  it: the file a finding is about, and an id, write out every character the file-name
  check can name (everything the map removes or changes, U+00AD and U+200D among them);
  keys and other paths write out the string set and a tab, a carriage return and a
  newline. FORMATS says so (c124655).
- A key holding a line break is now reported as an unknown key, with the key written out
  (`steps<U+000A>try`), not as `key: must be a one-line string` as on the record 11 build.

## Left out

- A safe character set for ids (spaces, commas, NFC against NFD): only what the map
  changes is checked.
- camelCase names: `deployProd` is one word and stays. Commands are not read: `ship: fly
  deploy` stays.
- Every well-formed emoji tag sequence (4), and keeping flags in the map.
- U+2800 (5).
- A length limit on `name` in `validate` (6).
- `.roostr/scan` that is not a regular file: it is run, not read, and `check` already says
  when it cannot be started.
