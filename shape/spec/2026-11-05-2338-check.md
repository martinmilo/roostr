## The problem this record serves

roostr is to be promoted alongside farmr, which runs coding agents in containers ("factory
runs"). A factory run commits after every iteration, then runs a gate command against the
committed tree in a separate container; the run passes only when the gate exits 0, and
otherwise the agent iterates again with the gate's output. The owner's requirement: when
agents change code, `.roostr/` stays current "99% of the time", by mechanism, not by a rule
in `AGENTS.md` that agents may ignore.

Nothing enforces it today. NEEDS ATTENTION is only shown and never changes the exit code,
and FORMATS.md says that nothing reports whether `entrypoints.tsv` is current.

So: one read-only command that answers "is `.roostr/` current with the code?", with exit
codes a harness can gate on. It is meant for four callers:

- farmr's factory gate: `roostr check --base main`;
- a Claude Code Stop hook committed in `.claude/settings.json`: `roostr check --base HEAD`.
  Verified by the coordinator: headless `claude -p` runs committed project hooks; exit 2
  from a Stop hook blocks the agent from finishing and feeds stderr back to it; exit 1 does
  not block; the hook fires after every turn, including turns that only answer a question;
- a Git pre-commit hook: `roostr check --base HEAD`;
- CI on pull requests: `roostr check --base origin/main`.

## Decided

### `roostr check [--base <commit>]`

- Read-only: never writes a file, not even `entrypoints.tsv`.
- Exit 0 when nothing is found, 1 with findings, 2 when it could not run.
- Findings go to stdout, as `validate`'s do. Reasons for exit 2 go to stderr.
- Works from any subfolder of the project, like the other commands. (No test pins this for
  any command yet; records 2 and 3 left it out. The program does it today. The tests of
  this record are the first to pin it.)

It reports four kinds of problem.

**1. Everything `validate` reports**, unchanged: the same findings, in validate's order.

**2. `entrypoints.tsv` is behind the code.** check runs `.roostr/scan` exactly as `roostr
scan` does (the same working directory, the same rules for accepting its output) but
compares instead of writing.

- A finding when the result differs from `entrypoints.tsv`. It lists the entrypoints added
  and removed, as `<kind> <name>`, and says to run `roostr scan`.
- A finding when the scan exists but `entrypoints.tsv` was never written.
- A scan that fails (non-zero exit, malformed output) is a finding, exit 1, not exit 2. It
  carries the same reasons `roostr scan` gives. The scan's stderr is shown only when it
  fails.
- A scan that is not executable is a finding too, exit 1: it is a problem in the
  repository that an agent can fix. (`roostr scan` exits 2 for the same file. The
  difference is deliberate: scan was asked to run the script and cannot; check was asked
  whether `.roostr/` is current and the answer is no.)
- With no `.roostr/scan` at all, this part is skipped and that is not a problem. roostr
  works without a scan.

Why this does not bring back the entrypoint rule record 3 dropped: that rule compared
commit order (a file named in `entrypoints.tsv` committed after `entrypoints.tsv`), so a
rescan that found nothing new could never clear it. This compares content. A rescan clears
it, and a code change that does not change the entrypoints never raises it.

**3. A process needs attention**, by exactly the rule the overview uses for NEEDS ATTENTION
(FORMATS.md, "What needs attention": reachability, uncommitted changes, records never
committed are skipped, a record with uncommitted changes counts as updated). The finding
names the process and the files, and says what to do: update `.roostr/processes/<id>.yml`,
or set `checked` to today's date if the record still holds. Today comes from `ROOSTR_TODAY`,
as everywhere else.

**4. A new entrypoint that no process lists**, only with `--base`: an entrypoint in the
working tree's `entrypoints.tsv` that was not in `entrypoints.tsv` at the base, and that no
record lists. The finding says to add it to a process's `entrypoints` or to describe a new
process.

- When the base has no `entrypoints.tsv`, this part is not compared, as `changes` does
  ("not compared"). Otherwise the pull request that first adopts roostr would fail on every
  undescribed route.
- Entrypoints that were already undescribed at the base are never reported. The overview's
  "N described" already shows that debt.

Parts 1, 3 and 4 take the working tree's `entrypoints.tsv` as "now". Part 2 compares it
with the scan.

### `--base <commit>`: judge only the work done after a commit

Without `--base`, check judges the whole project, old debt included: for CI on main and for
audits. With `--base <commit>` (anything Git accepts as a commit: `HEAD`, `main`,
`origin/main`, a hash; `--base=<commit>` is the same), it judges only the work done after
that commit. A hook must never block an agent on somebody else's old debt, because that is
what gets hooks deleted in real life.

- **Changed after the base** means touched by a commit reachable from `HEAD` and not from
  the base (Git's `base..HEAD`), or changed in the working tree: edited, staged, deleted,
  or untracked. The overview counts an untracked listed file as an uncommitted change (seen
  running the program today), and check does the same.
- Part 3 is limited to processes whose newer-than-record file also changed after the base.
  The finding lists only those files.
- Part 2 runs the scan only when the work could have changed the entrypoints (refined
  below). A turn that changed nothing, or an agent that only fixed records, runs no scan.
  The every-turn Stop hook stays instant, and a slow `rails routes` is not re-run when only
  records were edited.
- Part 4 as above.
- Part 1 (validate) is reported in full once anything changed after the base: its findings
  are objective errors in the current files and cheap to fix.
- **When nothing changed after the base**, check prints `No problems found`, runs no scan
  and exits 0. "Changed" means the same everywhere: not ignored by Git, inside the project
  folder, records included. (Decided on confirmation; see "Raised with the coordinator", 1.)
- `--base HEAD` therefore means "only uncommitted work". That is what the Stop hook and the
  pre-commit hook use. farmr's gate uses `--base main`, CI uses `--base origin/main`.
- **In a repository with no commits yet**, `--base HEAD` means that nothing is committed,
  so everything in the working tree is work after the base: validate in full, the scan
  runs, records are skipped as never committed, and part 4 is not compared because there
  is no `entrypoints.tsv` at the base. A pre-commit hook, or a template's global hooks,
  must not refuse a new project's first commit. Any other base that does not resolve there
  (`--base main`) is still refused. (Decided on confirmation.)

Could not run, exit 2, reason on stderr, nothing on stdout, nothing written:

- a base Git cannot resolve (a typo, or a commit missing from a shallow clone). The reason
  names the value, says it is not a commit in this repository, and that fetching more
  history may help. One message for both, because roostr cannot tell a typo from a commit
  it does not have;
- `--base` outside a Git repository;
- `--base` with no value;
- an option check does not take.

Without `--base`, outside a Git repository, check still runs parts 1 and 2, as the overview
works without Git.

### Refinements (**Proposed**, filling gaps in the brief; accepted on confirmation)

- **What makes the scan run under `--base`.** The brief says "when some file outside
  `.roostr/` changed". Proposed instead: the scan runs unless every file that changed after
  the base is a record (`.roostr/project.yml`, or a file under `.roostr/processes/`).
  Reasons: an agent that edits `.roostr/scan` itself, or writes it for the first time,
  should have it run; the brief's rule would skip both. Two more exclusions:
  - files Git ignores do not count. A Rails app writes `log/development.log` and `tmp/`
    all the time; if they counted, the scan would run on every turn, the Q&A turn included;
  - files outside the project folder (the folder that holds `.roostr/`) do not count. In a
    repository holding several projects, a change to another project does not run this
    project's scan.
- **"Differs" means the file differs.** The finding is raised when `entrypoints.tsv` is not
  byte for byte what `roostr scan` would write now. That includes a row whose file or area
  changed and a changed `# covers:` line, which list nothing as added or removed. A moved
  controller is the likely case, and `show` would otherwise point at a file that is gone.
- **"`entrypoints.tsv` at the base" is read at the merge base** of the base and `HEAD`: the
  commit where the work left the base. For `--base HEAD` that is `HEAD`. It differs from the
  base itself when the base has moved on since the branch left it: if `main` removed an
  entrypoint afterwards, the branch still has it, and reading `main` itself would report it
  as new on the branch.
- **No common commit, exit 2.** When the base and `HEAD` resolve but share no commit in the
  repository, check exits 2 saying that it cannot tell what changed after the base and that
  fetching more history may help. This is the usual CI checkout (depth 1): without the rule
  `base..HEAD` reaches back to the shallow boundary, every file looks changed, and all old
  debt is reported.
- **A merge commit** counts as touching only the files where it differs from every one of
  its parents. Merging `main` into a branch does not make `main`'s changes the branch's
  work. (Stated in FORMATS.md, no test of its own: see Left out.)
- **The scan's stderr, when it fails, is part of the finding on stdout**, indented under
  it, not passed to roostr's stderr as `roostr scan` does. The finding is then complete in
  one stream and in order; the Stop hook redirects stdout to stderr anyway, and a later
  JSON output would carry it inside the finding. When the scan succeeds its stderr is
  dropped.
- **No "not compared" note.** A clean run prints `No problems found` and nothing else, the
  same as `validate`, whether or not a scan exists and whether or not it ran. The Stop hook
  runs after every turn and anything printed there is noise to the agent; the overview
  already says `not scanned yet` for a project without a scan.

### Output (**Proposed**; accepted on confirmation)

Each kind of problem is a block: a heading in capitals, then a paragraph at an indent of
two that says what is wrong and what to do, wrapped at 80 greedy on spaces (the house
rule), then the items at an indent of four, never wrapped. Blocks are separated by one
blank line. The paragraph comes first so the reader knows what the list means before
reading it, and it names the file to edit, because the reader is often an agent blocked by
a hook with nothing else to go on.

Blocks, in this order, each left out when empty:

1. `VALIDATE`: validate's findings, one per line, as `validate` prints them, in its order.
2. `ENTRYPOINTS`: one of five forms (below). Added entrypoints with `+`, then removed ones
   with `-`, each group in `entrypoints.tsv` sort order, as `scan` reports them.
3. `PROCESSES`: by id in alphabetical order, the id at an indent of four and its files at
   six, in the order of the record's `files`. This is the `changes` layout.
4. `NOT DESCRIBED`: in `entrypoints.tsv` sort order.

With nothing found: `No problems found`, one line.

### `roostr --version`

`roostr --version` and `roostr -V` print `roostr <version>` on one line and exit 0, in any

Today both exit 2 as an unknown command. The tests pin the shape (`roostr X.Y.Z`), not the
number. The usage text (`roostr --help`, and the usage printed after an unknown command)

### `roostr init`

The line for `AGENTS.md` gains a last sentence. It stays one unbroken line:

```
When you need to understand this project's functionality, structure, or recent changes, run `roostr` for the project overview. Use `roostr show <id>` to inspect a specific process before modifying its behavior. After changing behavior a process describes, update its record, or set its `checked` date if the record still holds; after adding or removing an entrypoint, run `roostr scan`. Changed on confirmation (Raised 3): `--base HEAD` gives the line the same scope as the Stop
```
hook and the pre-commit hook, so agents are never sent after old debt, and "before each
commit" closes the gap of an agent that commits during its turn (`HEAD` is then the
parent of what it is about to commit).

A new section, CHECKS, after the `AGENTS.md` part and before SETUP. It hands the owner the
three ways to enforce the line; roostr itself never writes these files, as it never edits
`AGENTS.md`. The two snippets that are one line in a file are printed unbroken, like the
`AGENTS.md` line; every other line fits 80 columns:

```
CHECKS
The line asks agents to keep .roostr/ current; these make sure of it. Each runs
roostr check, which exits 1 when .roostr/ is behind the code and says what to
fix. With --base it judges only the work done after that commit. roostr writes
none of these files; the owner adds the ones they want.

Claude Code: merge this into .claude/settings.json. An agent then cannot finish
its turn while its uncommitted changes leave .roostr/ behind. If roostr cannot
run, the hook does not hold the agent back:

{"hooks":{"Stop":[{"hooks":[{"type":"command","command":"roostr check --base HEAD >&2 || { [ $? -eq 1 ] && exit 2; }"}]}]}}

Git: save this as .git/hooks/pre-commit and make it executable, so that a commit
that leaves .roostr/ behind is refused:

#!/bin/sh
roostr check --base HEAD

CI: run this on every pull request, with the full history fetched:

roostr check --base origin/main
```

The hook command maps check's exit 1 to exit 2, which blocks the agent, and lets every
other failure through as exit 1, a non-blocking error. A missing roostr (127) or a check
that could not run (2) therefore never traps an agent. Checked by running the shell line
with each exit code: 0 gives 0, 1 gives 2, 2 and 127 give 1. The JSON parses.

## Raised with the coordinator, and how it was settled

1. **A question turn blocked by old validate debt.** With validate always in full, a Stop
   hook on `--base HEAD` would block a turn that changed nothing whenever the project has
   any validate finding, from anyone, from any time: the agent asked "what does this
   function do?" would be made to edit `.roostr/` before it may answer. That is the
   old-debt block the brief wants to avoid. **Accepted:** with `--base`, when nothing
   changed after the base, check prints `No problems found`, runs no scan and exits 0;
   once anything changed, validate is reported in full. Scenario 147 flipped, 147a added.
2. **An agent kept going by a finding it cannot fix.** A scan that fails for a reason
   outside the repository (no database, gems missing in the container) is exit 1, so the
   Stop hook blocks every turn and farmr's gate fails every iteration. Claude Code ends a
   turn after 8 consecutive Stop-hook continuations, but the count resets whenever the
   agent calls a tool, so an agent that keeps trying can keep going (Claude Code hooks
   reference, "Stop decision control"). **Kept as decided**, as a known limit; the
   coordinator tells the owner.
3. **The soft rule and old debt.** "Run `roostr check` and fix everything it reports", with
   no base, would send every agent after all of the project's old debt on every task.
   **Changed:** the sentence names `--base HEAD` and "before each commit" (see `init`).
4. **`--base HEAD` misses work an agent commits itself.** If the agent commits during its
   turn, the Stop hook sees nothing uncommitted and passes. **Kept**, as a known limit. The
   new `AGENTS.md` sentence, the pre-commit hook, farmr's gate and CI cover it.
5. **A repository with no commits.** Refusing `--base HEAD` there would make a pre-commit
   hook refuse a new project's first commit. **Changed:** an unborn `HEAD` as base means
   that everything in the working tree is work after the base. Scenario 182 rewritten,
   182a and 182b added.

No existing test contradicts the brief. What changes in existing text is listed under
"Existing tests and text this record alters".

## Known limits

- An agent can be kept going by a finding it cannot fix (Raised 2).
- With `--base HEAD`, work the agent committed during its turn is not judged by the Stop
  hook (Raised 4).
- Any change to a record counts as an update (the first limit of NEEDS ATTENTION, which
  part 3 inherits). Writing a `checked` date, or any edit, clears a process.
