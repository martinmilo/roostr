## The problem this record serves

`roostr check` is meant to be the gate that keeps `.roostr/` current: a pre-commit hook, an
agent's Stop hook, CI. The QA found five ways to pass the gate with `.roostr/` behind, or to
be blocked with no way out: the hook judges the working tree, not the commit (G1); a merge
in progress blames the agent for the other side's work (G2); `checked` cannot change twice
on one day (G3); a scan helper that keeps stderr open hangs check (G4); deleting a record
silences NOT DESCRIBED (G5); a record saved as `.yaml` is ignored without a word (G6).

## Decided

### G1. `roostr check --staged`: the commit being made

`--staged` judges the commit that is being made, for the pre-commit hook. It works as
`--base HEAD`, and in addition reports a new block, **NOT STAGED**: every file roostr reads
under `.roostr/` (`project.yml`, the records `processes/<id>.yml`, `scan`,
`entrypoints.tsv`) whose working-tree state is not what is staged. That is an unstaged
edit, a new record Git does not track, and a deletion that is not staged. The commit would
leave the change out; the remedy is to stage it (`git add <path>`, which also stages a
deletion) or to undo the change. A file Git ignores, a hidden file and a file roostr does
not read (`.roostr/NOTES.md`, a `.yaml` file, see G6) never count.

- **Code files** are judged as with `--base HEAD`: stricter than the commit, never looser.
  **Proposed:** a code file has changed after `HEAD` when what is staged *or* what is in the
  working tree differs from `HEAD`. Judging the working tree alone would be looser than the
  commit in one case: a change staged and then undone in the working tree goes into the
  commit unseen (scenario 351).
- **Proposed: records are judged as they stand in the working tree,** as with `--base HEAD`.
  A record edit that is not staged then shows once, under NOT STAGED with its remedy, and
  not also under PROCESSES with a remedy ("update the record") that the agent has already
  followed (scenario 344).
- The scan runs on the working tree, as today. Running it against the index is left out.
- **Proposed:** NOT STAGED is the first block, before VALIDATE. The other blocks judge the
  files as they stand in the working tree; this one says which of them the commit would not
  hold. Paths in path order, relative to the project folder, as every path check prints.
  Text, wrapped by record 7's rules:

  ```
  NOT STAGED
    These files differ from what is staged, so the commit would not hold them as
    roostr read them. Stage each with git add <path>, or undo the change.
      .roostr/processes/join-waiting-list.yml
  ```

- `--staged` with `--base` (in either order, `--base=` too) is a usage error, exit 2, and
  the message says that the two cannot be used together.
  `--staged` outside a Git repository exits 2, as `--base` does. In a repository with no
  commits yet it means what `--base HEAD` means there (record 4), plus NOT STAGED.
- JSON: a new problem kind `not_staged` with `file`, the path as the text prints it
  (additive). **Proposed:** `base` is `"HEAD"` with `--staged`, and a new key `staged`,
  `true` or `false`, says which was asked (additive; `base: null` would read as "the whole
  project").
- During `git commit -a` and `git commit <path>`, Git runs the hook with `GIT_INDEX_FILE`
  naming a temporary index; roostr judges that index. Seen with Git 2.47.3: `commit -a`
  passes `<repo>/.git/index.lock`, `commit <path>` passes `<repo>/.git/next-index-<pid>.lock`,
  both absolute; a plain `git commit` passes `.git/index`, relative, also when the commit is
  started in a subfolder. Hooks start at the top of the work tree, so a subfolder project's
  hook does `cd services/shop && roostr check --staged`, and then the relative path no
  longer leads to the index. Git itself reads a relative `GIT_INDEX_FILE` from the top of
  the work tree after such a `cd` (tried); roostr does the same.
- init: the Git pre-commit snippet becomes `roostr check --staged`, and CHECKS' opening
  paragraph says what `--staged` judges. The Stop hook keeps `--base HEAD` (an agent
  mid-turn has staged nothing), and so does the line for AGENTS.md.

Accepted cost, from the brief's "stricter than the commit": a commit of `README.md` alone,
while a listed file has uncommitted work and its record is unchanged, is refused (tried:
`check --base HEAD` lists the process; `--staged` will too). The way out is to update the
record or `git stash push --keep-index` before committing.

### G2. A merge in progress

While a merge is in progress (`MERGE_HEAD` exists), check answers as it will once the merge
is committed with the tree as it stands. The merge is then a merge commit, whose parents
are `HEAD` and the merged commits, and by FORMATS' rule it touches only the files in which
it differs from every parent. So during a merge a file has uncommitted changes only where
the working tree (and, for `--staged`, the index) differs from `HEAD` and from every merged
commit. A conflict resolution that differs from both sides is work, as it is in a merge
commit; a file taken whole from one side is not.

With `--base HEAD` and `--staged`, the merged commits count as part of the base: what the
other side did was judged where it was made, and only what the merge itself changes is the
agent's work. Without `--base`, and with any other base, the merged side's commits count
as they will once the merge commit reaches them.

**Raised 1, accepted in place of the brief's "a record updated on the merged side counts
as updated":** the same rule for records as for code. A record counts as updated by the merge
only where it differs from every parent; a record taken whole from the merged side has that
side's history, as it will after the commit. The brief's clause is today's behaviour for
records, and it lets the hook pass a merge that `check` fails right after it is committed.
Tried on the frozen build (`qa-a2/repos/shaper-g2b`): the branch and `main` both change
`app/orders.rb`, `main` also adds `checked:` to `place-order`; the merge stops on a
conflict, resolved to a third version. Mid-merge `check --base HEAD` prints `No problems
found`. After the merge commit, `check` and `check --base main` both list `place-order`
`app/orders.rb`, exit 1. If the merge also edits the record (`shaper-g2c`), both pass after
the commit. The clause also makes a gate run mid-merge disagree with itself: merging `main`
into a branch, with `--base main`, the record `main` updated clears the branch's own change
during the merge (`shaper-g2`: `No problems found`) and not after the commit (PROCESSES,
exit 1). With the single rule, a mid-merge answer is the one check gives after the merge
commit; scenarios 369 and 370 pin it.

"What needs attention" is shared with the overview, so the overview's NEEDS ATTENTION
during a merge follows the same rule. Rebase and cherry-pick in progress are not special:
the replayed change is the agent's own work (scenario 372). An octopus merge has several
merged commits; "every merged commit" covers it (no test).

### G3. `checked` with a time

`checked` is a date, `YYYY-MM-DD`, or a date and time, `YYYY-MM-DD HH:MM`: one space, local
time, 24-hour, hours and minutes of two digits each. validate accepts both and nothing else
(`2026-10-10T14:30`, `2026-10-10 24:00`, `2026-10-10 14:30:15` and `2026-10-10 9:30` are
findings; the finding gives both forms). JSON `checked` is the value as written. `show`
prints it as written. Roostr still compares it with nothing.

check's PROCESSES paragraph suggests a value for `checked` that differs from what each
listed record holds:

- the date alone, `checked: 2026-10-10`, when no listed record holds today's date;
- otherwise today's date and the current time, `checked: 2026-10-10 14:30`;
- and if a listed record holds that minute already, the next minute (`14:31`; at `23:59`,
  `2026-10-11 00:00`).

**Proposed:**

- **Minutes, never seconds.** `2026-10-10 14:30` is a plain string in YAML 1.2 and in YAML
  1.1 too, whose timestamps need seconds: Ruby's Psych reads it as a string and
  `2026-10-10 14:30:15` as a time (tried). Other tools that read records stay safe.
  The next minute is at most a minute ahead, and nothing compares it.
- **One value per block.** The paragraph names one value for every process it lists, as
  today, so the value differs from every listed record's `checked`.
- **The clock handle:** `ROOSTR_TODAY` takes `YYYY-MM-DD` or `YYYY-MM-DD HH:MM`. A date
  alone means midnight, so a test that sets a date only gets `00:00`, never the machine's
  time. One variable keeps date and time from contradicting each other. The last 7 days and
  `--since` count days as before.

### G4. A scan helper that keeps stderr open

check returns as soon as the scan script has exited and its stdout is closed, as `roostr
scan` does. When the script fails, it shows what the script wrote to stderr until then. A
child that holds stdout open still blocks both commands: its output is not complete.

### G5. NOT DESCRIBED: one rule

With `--base`, an entrypoint in `entrypoints.tsv` (the working tree's) that no process lists
is reported, unless at the base it was already in `entrypoints.tsv` and no process listed
it there: old debt stays quiet. The base is the merge base of the base and `HEAD`, as today,
for `entrypoints.tsv` and now for the records too. The rule covers a new entrypoint (today's
case) and one that lost its description: its record deleted, or the entrypoint dropped from
the record's list. Moving an entrypoint to another record is not reported, and neither is
removing a feature (its record and its rows gone).

The paragraph reads right for both:

```
NOT DESCRIBED
  No process lists these entrypoints, though at HEAD each was either new or
  listed by a process. Add each to the entrypoints of the process it belongs to
  in .roostr/processes/<id>.yml, or describe a new process for it. Where a
  process listed it before, restore that record or its entry instead.
```

**Proposed:**

- **No `entrypoints.tsv` at the base: not compared, as today.** Taken literally, the single
  rule would report every undescribed entrypoint in the first commit that adds
  `entrypoints.tsv`, which blocks adoption. Without a baseline check cannot tell old debt
  from new; the existing test keeps its meaning.
- **A record that is not readable now** is taken to list what it listed at the base, so a
  broken record shows once, under VALIDATE, and its entrypoints do not also appear under
  NOT DESCRIBED. It opens no escape: VALIDATE already exits 1.
- A record at the base that roostr cannot read lists nothing there.
- JSON keeps the kind `not_described`.

### G6. Record-like files roostr does not read

A file in `.roostr/processes/`, or in a folder below it at any depth, whose name ends in
`.yml` or `.yaml` in any letter case and is not an `<id>.yml` directly in
`.roostr/processes/`, is a validate finding (so check's VALIDATE reports it too). The
finding is `<file>: <message>`; the message says that a record is a file named `<id>.yml`
directly in `.roostr/processes/`, in those words, which the tests look for. Other files (a README, notes) stay ignored. The overview and `show` are
unaffected.

**Proposed:**

- The finding names the file to rename or move it to when that is clear: the same name with
  `.yml`, directly in `.roostr/processes/` (`refund-booking.yaml` and
  `bookings/refund-booking.yml` → `.roostr/processes/refund-booking.yml`; `Refund.YML` →
  `Refund.yml`, ids are as written). When a file of that name exists already, it names none.
- Hidden means a name starting with `.`, of the file or of any folder on its path below
  `.roostr/processes/` (`.drafts/refund-booking.yml` is hidden).
- JSON: kind `invalid`, `key` and `line` `null`, as any finding about a whole file.

### G7. FORMATS: the sort order of `entrypoints.tsv`

FORMATS lists among validate's checks that the rows of `entrypoints.tsv` are in byte order
of their whole line, and that the finding names the line of the first row out of order

### Docs: gates and the working tree

FORMATS, wherever it describes `--base` for gates: a gate that runs where the agent worked
judges the working tree too, so it should run on a clean checkout of the commit (as CI
does), or after the harness has committed everything. `--staged` is for the pre-commit hook
only. README is the coordinator's.

   hook at the top of the work tree, so init's snippet `roostr check ...` there cannot find

   the same snippets as at the top.

   Decided: when `.roostr/` is below the top of the repository, init prints the pre-commit
   and CI commands with `cd <folder> && ` in front. The folder is the project folder
   relative to the top, as `git rev-parse --show-prefix` gives it, without its final `/`:
   `cd services/shop && roostr check --staged`. When the folder holds anything but letters,
   digits and `_ . / -`, it is quoted for sh: in single quotes, a `'` in it written `'\''`
   (`cd 'apps/my atelier' && roostr check --staged`). At the top, and outside a Git
   repository, the commands are as before. The Stop hook is unchanged: it runs wherever the
   agent's session started, which init cannot know. Scenarios 408 and 409.
