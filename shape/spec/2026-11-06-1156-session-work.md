# Part A: the AGENTS.md line for agents that read another file

## The problem

`roostr init` tells the owner to add one line to AGENTS.md. The line asks agents to read
the overview, update records, and run `roostr check --base HEAD` before each commit and
before they finish. An agent that does not read AGENTS.md never gets it. The project map
of record 10 reaches Claude Code through the SessionStart hook either way, but the map does
not ask the agent to keep `.roostr/` current; the line does.

## What the tools do

- **Claude Code** (code.claude.com/docs/en/memory, "AGENTS.md"): it reads AGENTS.md only
  when there is no `CLAUDE.md`, `.claude/CLAUDE.md` or `CLAUDE.local.md` in the working
  directory or above it; with one, it reads the CLAUDE.md files only. A line `@AGENTS.md`
  in CLAUDE.md imports it, and "never makes Claude read AGENTS.md twice". The coordinator's
  probe on Claude Code 2.1.319 with default settings agrees: AGENTS.md alone was read;
  AGENTS.md beside an unrelated CLAUDE.md was not; a CLAUDE.md holding `@AGENTS.md` was.
- **Gemini CLI** (geminicli.com/docs/cli/gemini-md): context files have "the default name
  `GEMINI.md`"; "to specify a different name or a list of names, use the
  `context.fileName` property", whose example lists `AGENTS.md`. A GEMINI.md imports other
  files "using the `@file.md` syntax".
- **Codex** (learn.chatgpt.com/docs/agent-configuration/agents-md): "Codex reads
  `AGENTS.md` files before doing any work."
- **Cursor** (cursor.com/docs/context/rules): "Cursor supports AGENTS.md in the project
  root and subdirectories."

## Decided

**A1. init's AGENTS.md section.** After the line, before CHECKS, one paragraph, exactly as
printed:

```
Claude Code reads AGENTS.md only where the project has no CLAUDE.md, and Gemini
CLI reads GEMINI.md unless set otherwise. For them, CLAUDE.md or GEMINI.md holds
a line @AGENTS.md, which brings AGENTS.md in, or the line above itself.
```

`@AGENTS.md` comes first because it keeps one file for every tool; the line itself is for
an owner who wants it in CLAUDE.md. The heading `AGENTS.md` and the sentence above the line
are unchanged.

**A2. SETUP's last paragraph**, in place of "Do not commit and do not edit AGENTS.md. The
owner reviews .roostr/ first and adds the line.":

```
Do not commit, and do not edit AGENTS.md, CLAUDE.md or GEMINI.md. The owner
reviews .roostr/ first and adds the line.
```

**A3.** init still writes only `.roostr/project.yml`: never AGENTS.md, CLAUDE.md or
GEMINI.md.

**A4. FORMATS and the README.** FORMATS does not mention AGENTS.md (init's text is pinned
by the tests), so it needs no change for Part A. The README, where it tells the owner to
add the line to AGENTS.md:

> GEMINI.md: give them the line with a line `@AGENTS.md` in that file, which imports
> AGENTS.md, or with the line itself.

# Part B: what a session's work is

## The problem

Record 9 judges a session as `--base <the commit it started at>`. The QA round found that
this credits the agent with work it did not do, which holds it at Stop for nothing, and
in two places lets work through:

1. Uncommitted work from before the session (repro 1, HIGH): a user with half-done edits
   starts Claude Code to ask a question, and Stop holds the agent for code it never
   touched. Repro 9 is the same rule the other way: a record the user had edited before
   the session counts as the agent's update, and a stale record passes.
2. Commits brought in (repro 2, HIGH): `git pull`, checking out a teammate's branch,
   `git reset --hard origin/main`. Record 9's Raised 3 (merging `main` after the session's
   commits) is the same case. The reviewer added: GitHub's squash and rebase merges write
   new commits, dated when they are merged, so a pull request merged during the session
   and then pulled looks new; and `git pull --rebase` replays the user's own commits.
3. Plan mode (repro 7): the agent cannot edit, so Stop holds it again and again.
4. A worktree entered mid-session (repro 4): records are per Git folder, so the new
   worktree has none, and the session passes as `--base HEAD`.
5. Input over 1 MiB (repro 8): Stop input can carry the last assistant message; over 1 MiB
   it is no input, and the session passes as `--base HEAD`.
6. Messages (repro 10): NOT DESCRIBED names a 40-character hash; an unrelated history gets
   the `--base` and shallow-clone message, for options the hook never passed.
7. Left as is, documented: repro 5 (switching back to `main` hides the branch's commits),
   repro 3 (the scan runs every turn once the session has work).

The reviewer's further points: the user's uncommitted files reach VALIDATE and
ENTRYPOINTS too; an agent that cannot fix what Stop reports is held without end, since
Claude Code's own limit of 8 holds in a row starts again at every tool call; and a session
start time noted to the minute, compared with commit dates, is open to a lagging clock.

## Decided

### B1. The working tree as it was when the session started

`roostr session start` notes, besides the commit, the state of every file that differs
from that commit in the work tree, as `git --no-optional-locks status
--untracked-files=all` lists it: edited, staged, deleted, and not tracked but not ignored.
For each, its content as `git hash-object --no-filters` computes the blob id (no object is
written, and no clean filter runs: Git LFS's writes into `.git/lfs`), or that it is
deleted. A submodule, or a repository nested in the work tree that Git lists as one
untracked entry, is noted by the commit its `HEAD` is at, never hashed: today such an entry
makes `hash-object` stop, and the whole snapshot with it. It also notes the work tree it
ran in.

**Order and budget.**

- It writes the record (the commit, the time, the identity of B2) first, then takes the
  snapshot and adds it. A slow snapshot never costs the record or the map: Claude Code
  stops the hook at its 10 seconds and drops its stdout.
- Only the session start that creates the record takes a snapshot. Every later one for the
  same id (resume, compact, clear) keeps the record and its snapshot as they are.
- A file larger than 8 MiB (8,388,608 bytes) is noted by its size and modification time,
  and not read.
- The snapshot has 3 seconds, counted from when it begins. Files not hashed by then are
  noted by size and modification time. When `git status` itself has not answered by then,
  it is stopped and no snapshot is kept: every uncommitted change then counts as the
  session's, as in record 9.

**Why 3 seconds and 8 MiB.** The reviewer measured the snapshot of a tree of 100,000
tracked and 30,000 untracked files at 1.3 s with a warm cache; 3 s covers that twice over.
With record 10's 2 seconds for stdin and the map, session start stays near 6 s of the 10
Claude Code gives it. Source files, lockfiles and most generated files are well below
8 MiB; one large file (a database dump, a video) would otherwise spend the budget alone.
Size and modification time are what Git itself trusts before it reads a file again.

**At Stop**, in the work tree the snapshot was taken in, a file's uncommitted change is the
session's unless the file is as the snapshot noted it: the same content, deleted then and
now, the same size and modification time for a file noted so, the same commit for a
submodule or nested repository. A file the user left edited, deleted or new, and the
session did not touch, is as if unchanged. In any other work tree, and when no snapshot was
kept (or the record was written by an earlier version), every uncommitted change is the
session's.

- This is the rule for records too (repro 9): a record's uncommitted changes count as an
  update only when they are the session's. A record the user edited before the session is
  judged by its last commit.
- A file whose pre-session change the session commits (`git commit -a`) is touched by a
  session commit (B2), so it is the session's work. This errs strict: the agent committed
  it.
- `git stash` and `git stash pop` in the session leave the user's files with their content
  as noted: not the session's. A formatter that re-saves a file the user changed, with a
  change of its own, makes it the session's.
- A file noted by size and modification time that is saved again unchanged counts as the
  session's. Errs strict, documented.
- **Inherent, documented:** roostr cannot tell who changed a file during the session. The
  user saving files in their editor, and a second session in the same work tree, count as
  this session's work (record 9's tests for two sessions stand).
- **Not taken:** `git stash create`, which may refresh the index.

### B2. A commit is the session's when this session's committer made it after the start

A commit is the session's work when all of these hold:

1. It is reachable from `HEAD` and not from the start commit.
2. It is not a replay: not patch-identical to a commit the start commit reaches, as `git
   rev-list --cherry-pick --right-only <start>...HEAD` leaves out (the reviewer verified
   that this drops the replays and keeps the agent's commit). A replay in which the agent
   resolved a conflict differs from the original, so it counts. This also covers a
   reword-only amend of the start commit (repro 6).
3. Its committer email is the one `git var GIT_COMMITTER_IDENT` gave at session start. When
   Git had no committer identity then, this condition is left out.
4. Its committer date (`%ct`) is not more than 5 minutes before the session started. The
   start is noted in seconds since the epoch, by roostr's clock (`ROOSTR_TODAY` in the
   tests).

**The identity on every commit (decision).** The coordinator preferred it on every commit;
the reviewer applied it only to commits a remote-tracking ref reaches. Taken: every commit.
It is one rule, stated and tested once. A commit can reach `HEAD` without any
remote-tracking ref (`git pull <url> <branch>`, which merges `FETCH_HEAD`; a branch from a
second clone; refs pruned by `git fetch --prune`), and whether a ref happens to exist would
change the answer. The session's own commits are made where the hook runs, Claude Code's
Bash and its hooks sharing one environment, so they carry the identity noted. The cost: an
agent that commits under another identity (`git -c user.email=...`, or `git config`
changed in the session) is not judged at Stop; documented, with backdating, under B7. The
pre-commit hook still judges each commit, and CI the branch.

**The tolerance: 5 minutes (decision).** The hook and a commit can read different clocks:
an agent that commits inside a container whose clock lags the host's (Docker Desktop's
virtual machine after the host slept), or a clock stepped back by NTP. Five minutes covers
a lag of that kind. What it costs: a commit by the same committer, dated in the 5 minutes
before the session and not reachable from where it started (the user's own branch, merged
in the session), counts. The wider the window, the more of the user's own work just before
the session would count; that is why it is not wider.

So: `git pull`, a teammate's branch checked out, `git reset --hard origin/main`, a pull
request squash-merged on GitHub (GitHub is its committer) and then pulled,
a commit from a machine whose clock is ahead, and `pull --rebase` replaying the user's
unpushed commits: none of them is the session's. A merge commit the session makes is
new and touches only the files where it differs from every parent, as before: merging
`main` after the session's own commits counts only what the merge itself resolved (record
9's Raised 3, settled). Commits the session makes on a side branch and merges with
`--no-ff` count. An amend of the session's own commit counts.

With B1 and B2, a file is the session's work when a session commit touched it or its
uncommitted change is the session's. Everything `--base` says about "changed after the
base" then holds for these files: nothing of them, `No problems found` and no scan; the
scan runs unless they are all records or `project.yml`; PROCESSES lists only them.

In the tests `reminder_job_changed_and_committed` moves from 2026-10-09 to 2026-10-10
(noon UTC; sessions in the tests start at 00:00 that day), and the kit's teammate commits
default to 2026-10-09.

### B3. Plan mode does not hold the agent

When the Stop hook's input has `permission_mode` `plan`, `check --session` does not judge:
it prints `Not judged: the session is in plan mode, where the agent cannot change files.`
on stdout and exits 0. It runs no scan. The next turn that ends outside plan mode is
judged as ever, with everything done since the session started. With `--json`, `problems`
is `null`. `stop_hook_active` stays unused: using it would let an agent through on its
second try without fixing anything. Every other mode Claude Code has (`default`,
`acceptEdits`, `auto`, `dontAsk`, `bypassPermissions`), and any other value, is judged.

### B4. Session records in the repository's common Git folder

Records go to `<git common dir>/roostr/sessions/<session_id>`, the folder `git rev-parse
--git-common-dir` names: `.git` in a checkout and in every linked worktree of it. A session
that moves into a worktree it created finds its record there; with B2, its commits there
are its work wherever it started. With B1, its uncommitted changes in the new worktree are
all its own.

- This helps only when the Stop hook runs in the new worktree. After `git worktree add
  ../x && cd ../x` in Bash, Claude Code may still run the hook in the original checkout,
  where the work in `../x` is not seen. Documented.
- Records written by record 9 in `.git/worktrees/<name>/roostr/sessions/` are no longer
  read: a session started in a linked worktree before the upgrade is judged as `--base
  HEAD`. Harmless, and they go when the worktree does.

### B5. Input up to 16 MiB, and a line when the session cannot be judged as one

`session start` and `check --session` read stdin until it ends or 2 seconds have passed,
and keep at most 16 MiB; what comes after is read and dropped, so the runner gets no broken
pipe. Input over 16 MiB is no input. Record 10's 1 MiB limit goes.

`check --session` judges as `--base HEAD` with one line on stderr when the input is over
16 MiB (`roostr check --session: the input on stdin is over 16 MiB; judged as --base HEAD`)
and when the input names a session it has no usable record of: no record, or the commit
the record names no longer exists (`roostr check --session: no usable record of session
<id>; judged as --base HEAD`). Input that names no session (empty, not JSON, no
`session_id`, one it would not use as a file name) is judged as `--base HEAD` without a
word, as before: a runner that passes no input is not a mistake.

### B6. Messages under `--session`

- NOT DESCRIBED's paragraph says "though when the session started each was either new or
  listed by a process" in place of "though at <base> each ...".
- When `HEAD` shares no commit with the start commit (an orphan branch): exit 2, as now,
  with `Cannot judge the session: HEAD shares no commit with the commit it started at,
  <short hash>.` on stderr. No `--base`, no shallow clone. The Stop hook then exits 1, an
  error that holds nothing.

### B7. Left as is, and written into FORMATS

- Switching back to `main` before finishing (repro 5): the branch's commits are no longer
  reachable from `HEAD`, so they are not judged. The pre-commit hook judged each commit,
  and CI judges the branch.
- Amending the start commit with a change of content: the amended commit is new and not a
  replay, so everything it holds counts as the session's.
- The scan (repro 3): it runs every turn once the session has work other than records.
- Once the session has work, VALIDATE and ENTRYPOINTS judge the whole project but the
  files left by the user: what was already wrong in the commits is reported then too.
- Ways around the Stop hook: a commit backdated more than 5 minutes before the session
  (`GIT_COMMITTER_DATE`, `git rebase --committer-date-is-author-date`), or made under
  another committer identity, is not the session's. The pre-commit hook and CI still
  judge it.

### B8. The user's files leave VALIDATE and ENTRYPOINTS too (reviewer #4)

A file **left by the user** is one the snapshot noted, that is still as noted, and that no
session commit touched. Under `--session`:

- VALIDATE leaves out the findings in a file left by the user (a record the user is
  editing).
- ENTRYPOINTS compares the scan's output and `entrypoints.tsv` without the rows whose file
  is left by the user (a route in a controller the user is writing, not scanned yet). The
  `# covers:` line is compared as ever.
- NOT DESCRIBED is compared, as before, with `entrypoints.tsv` and the records at the merge
  base of the start commit and `HEAD`, and only when `entrypoints.tsv` or a record is the
  session's work.

A finding in a record the user did not change, caused by the user's change elsewhere (a
rescan that dropped an entrypoint the record lists), is still reported. Documented.

### B9. No endless holds

When `check --session` would hold for the fourth time in a row with the same problems and
no change in the session's work, it exits 0 instead and prints one line:

```
Not held again: 3 holds in a row found the same problems and no change to the session's work. The problems remain; the pre-commit hook and CI will report them.
```

- **Same problems**: the problems as `--json` lists them, not the text, whose `checked`
  suggestion moves with the clock.
- **No change in the session's work**: the same session commits, and the same content of
  every file whose uncommitted change is the session's.
- The count is kept beside the session's record, in the same folder of Git's; `check`
  still never writes the working tree. It goes when the record does. When it cannot be
  written, check holds as ever.
- A run that does not hold (it passes, or does not judge: plan mode) starts the count
  again. The fifth identical run is let through too.
- Only the text output counts and is let through. `--json` is read by programs, which
  decide for themselves; it neither counts nor is let through.
- Why 3: one hold to report, one to try again, one more for an agent that misread it.
  Claude Code's own limit is 8 holds in a row, but it starts again at every tool call, so
  an agent that runs a command between Stops is never let through by it.

# Part C: the map's groups, and session start's exits

**C1. One `other`.** A record whose group is literally `other` and the processes without a
group gave two `other:` headings, and in form (b) the first sorted among the named groups.
The overview already puts them under one `other`. Decided: they are one group, `other`,
listed last, after every named group, whatever its name (a lower-case `stock` too).

**C2. A stdout that cannot be written.** `session start` exited 2 when stdout is
`/dev/full` ("No space left on device"). FORMATS says it exits 0 whenever it ran, and a
closed stdout and a broken pipe already exit 0. Decided: 0 also for a failed write; the
record is written all the same. On systems without `/dev/full` (macOS) the test is skipped.

**C3. A current folder that was deleted.** `session start` run in a folder that no longer
exists exited 2 (`Cannot read current directory`). Decided: exit 0, nothing recorded,
nothing on stdout, and one line on stderr in session start's form: `roostr session start:
the current folder no longer exists; nothing recorded`. `check --session` there keeps exit
2: it cannot judge, and exit 2 is "could not run", which the Stop hook already lets
through; 0 would claim a pass. Its stderr says the current folder no longer exists.

**C4. Values that strip to nothing.** In the map, a value that is empty once the hidden
characters of record 10 are dropped counts as absent: `stack: "<U+200B>"` gave `Stack: `,
`group: "<U+200B>"` a heading of just `:`, `watch_out: [""]` a line `- `, and `files:
[""]` empty brackets. Decided, for the map: such a stack or description has no line; a
watch-out item, an operation note, an operation (empty name or command) and a files item
are left out; a group is no group; a process description makes the process `- <id>
[<paths>]`, as form (a) lists it.

Groups are told apart by their name **as the map prints it**, stripped: `Book<U+200B>ings`
and `Bookings` are one group, `Bookings`, as the record 10 build already does. One rule
then covers C1 and C4: the map groups by the printed name, and a name that is empty, absent
or `other` is `other`, last. The overview keeps its own rule (names as written); `validate`
reports the hidden character either way.

**C5. A note for the worker, no test.** Form (c) computes the size again for every line it
removes, which is quadratic: about 8,000 groups take 1.6 s. A running total keeps it
linear.

## Test kit

- `check_session permission_mode: "plan"` and `last_assistant_message: "..."`: keys of the
  Stop hook's input; `claude_code_runs ..., permission_mode:` too.
- `commit "...", on:, from: "second-checkout"`: a commit in a linked worktree.
- `teammate_pushed_a_change_to path, on:, branch:, fetched_from_a_url:`: a commit by A
  Teammate on `origin/<branch>` (or in `FETCH_HEAD`), made with Git's plumbing so that
  `HEAD`, the index and the working tree stay as they were; dated 2026-10-09 by default.
- `pull_request_squash_merged_on_github path`: the same, committed by GitHub during the
  session (as `GitHub <noreply@example.com>`: the hook that keeps this repository
  public takes only example.com addresses).
- `agent_runs_git "rebase", "origin/main"`: git as the agent runs it in the session, its
  commits dated 2026-10-10 12:00 UTC; `rebase_onto_origin_main_resolving_a_conflict_in
  path`.
- `saved_again_unchanged path` (a later modification time), `formatted path` (a
  `# frozen_string_literal: true` line on top, as RuboCop adds it), `edited_to_a_size_of
  path, bytes`, `nested_repository path`, `untracked_files_under_a_clean_filter`.
- `session_start env: a_git_whose_status_never_answers`: a git on the `PATH` that hangs on
  `status` and passes everything else to the real one.
- `session_held 3`: `check --session` run that many times, each holding.
- `stdout: :full` (skipped where there is no `/dev/full`), and `from_a_deleted_folder:
  true`.
- `atelier_halfway_through_the_waiting_list scanned: false`: the same work, with
  `entrypoints.tsv` as committed.
- `reminder_job_changed_and_committed` on 2026-10-10, committing only that file, so that
  the user's uncommitted work stays uncommitted.
- `the_user_left_edited path`: the user's own change, uncommitted, before the session.
