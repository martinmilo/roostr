## The problem this record serves

Each finding is a case likely in real use: CI and containers clone shallow; agents copy ids
from the overview and append keys to records; editors on Windows add a BOM and CRLF; Emacs
leaves lock files; CI pipes output through `head`. In each, roostr either gave a confidently
wrong answer (a false green, a cut id that does not exist) or refused a whole project over
one harmless slip.

## Decided

### F1. A shallow clone never gives a false green

Seen (`repro-shallow.sh`): in a clone of depth 1, `needs_attention` is `[]` and `roostr
check` exits 0, while the full clone of the same history exits 1 with two processes;
`changes` credits the oldest commit in the clone to processes it never touched. The oldest
commit of a shallow clone looks as if it added every file, records included, so every
record looks updated in it: the wrong direction.

In a shallow repository roostr cannot know what is newer than what, so:

- The overview prints, exit 0, leaves out LAST 7 DAYS, and NEEDS ATTENTION has the note of
  record 6 with the reason that the history is shallow, and how to fetch it in full:
  `git fetch --unshallow`. `roostr --json`: `needs_attention: null`.
- `changes`: exit 2, with that reason.
- `check` without `--base`: exit 2, with that reason, also suggesting `--base`.
- `check --base <commit>` works when the history after the base is complete in the clone.
  The coordinator's condition, that the merge base of the base and `HEAD` is in the clone,
  is not enough: Raised 1 shows a false green it lets through, and proposes the condition
  that is. Under it, a record whose last commit lies beyond the clone's edge looks updated
  at the edge, which is at or before the base; every file that changed after the base is
  then newer than it, as it truly is. The common hook, `check --base HEAD` in a depth-1
  clone, meets it: the edge is `HEAD`.

### F2. Identifiers are printed whole

Seen (`repro-truncid.sh`, `repro-longpath.sh`, and this record's own probe): the overview
cuts ids over 36 characters to `...`, so two ids can print the same and an agent that copies
one gets "No process with id ... exists"; areas, groups, outcome, operation and environment
names are cut the same way; `show` and NEEDS ATTENTION break long paths in the middle of a
word (`remin` / `ders`), and `show` splits an entrypoint over two lines; a long command
wraps. No record allowed any of it: records 1 and 1a made each column "as wide as the
longest id shown plus three spaces", with no limit; record 1 let a `show` line "pass column
80 rather than cut a file path"; record 1a said "A command or note is never cut; the line
may pass column 80"; record 1b withdrew the one `...` rule, for descriptions.

- Ids, paths, entrypoints (`<kind> <name>`, never split at its space), area and group
  names, outcome, operation and environment names are printed whole, never cut or broken.
  A line may run past 80 columns for them.
- Prose (descriptions, notes, `why`, the text of an outcome, an environment's value, the
  paragraphs of `check`, the sentence after a path in NEEDS ATTENTION) keeps wrapping at
  spaces within 80 columns.
- **Proposed**, the layout: a label column (ids in FUNCTIONALITY and NEEDS ATTENTION,
  areas, operation, environment and outcome names) is as wide as the longest name it
  shows, but never wider than 36 characters, plus its gap. A name of more than 36
  characters stands alone on its line, printed whole, and what would have
  followed it starts on the next line, in the column. So one long id does not push every
  description on the screen into a narrow strip or past column 80, as a column grown to the
  longest name would; and nothing is cut. This is how most `--help` screens show a long
  option. 36 is the longest the overview shows an id today, cut or not; the alternative,
  the coordinator's words read literally, is a column grown to the longest name with lines
  past 80, and would have changed no scenario below but 275, 276, 278, 280, 282, 283 and 286.

  ```
    reminder_scheduling_and_dunning_administration
                                         http 1
      send-payment-reminder-to-overdue-clients-by-email
                                           Mail each client whose invoice is
                                           overdue, once a week.
      refund-invoice                       Refund an invoice to the card it was
                                           paid with.
  ```

  Prose wraps at spaces; a word longer than the room left (a path) is printed whole on a
  line of its own, past column 80 when it must.
- An operation's command is printed whole too, never wrapped, as record 1a said: a
  command is copied, not read, and a wrapped one pastes as two lines. (**Proposed** only
  in that the coordinator's list did not name it.)

No existing test pins a cut. `test/overview/functionality_section_test.rb` refutes `...`
for a long description, which stays true. No frozen screen has a name long enough to
change.

### F3. A key written twice is a finding

Seen (`repro-dupkey.sh`): an agent appended a second `files:` list; the first vanished
silently and its files stopped being watched. YAML 1.2 requires unique keys, and agents
append (often `checked:` to a record that has one).

- `validate`, and so `check` and `invalid` in JSON, reports a key written twice in any
  YAML file, at any level, on the key's dotted path (`files`, `outcomes.refunded.when`),
  naming both lines in the message.
- The coordinator leaned to readable; **decided here, Proposed**: the file stays readable
  and the last value counts, what an agent appending a new `checked:` meant. This is an
  exception to record 5's readable rule, stated as such: a key written twice is about the
  record's own content, but hiding the process from the overview and from farmr over an
  appended line would cost more than the finding, which `check` already makes blocking.
- **Proposed**: the lines go in the message; `line` in JSON stays `null`, since record 5
  defined it as a line of `entrypoints.tsv`.

### F4. An empty value is an absent value

Seen (`repro-empty-group.sh`, and this record's probe): `group:` and `try:` left empty come
out as `""` in JSON, where FORMATS.md says `null`, while the text treats them as absent; an
empty command prints as a blank. `stack:` left empty is already `null`. Worse, other empty
keys refuse the whole file: `checked:` ("must be an existing date"), `operations:` and
`environments:` ("must be a map"), and `watch_out:` ("must be a list"). Uncommenting
`# watch_out:` in the file `init` writes, without its commented items, gives exactly that,
and the overview exits 2. `init`'s file says "Remove the "# " in front of a key to use it",
so this is likely.

- Any key whose value is empty (YAML's null, or the empty string) is treated exactly as if
  it were absent, in text, JSON and `validate`: an optional key is simply not there; a
  required one (`name`, `description`) is missing, a finding as before.
- An operation whose command is empty (`test:` with nothing after it, or `command:` empty)
  is a `validate` finding, and does not make `project.yml` unreadable.
- **Proposed**: such an operation is left out of the overview and of the JSON, which has
  nothing to say about it (a JSON `command` is always a string). An environment with an
  empty value is treated the same way: a finding, left out.

### F5. A byte order mark is ignored

Seen (`repro-bom.sh`): a UTF-8 BOM at the start of `project.yml` or a record gives
"unknown key" and "name is required" findings and stops the overview. Windows editors add
one; YAML 1.2 allows it.

- A UTF-8 BOM at the start of `project.yml` or a record is ignored.
- **Proposed**: also at the start of `entrypoints.tsv` when it is read. `check` still
  reports such a file as not what `roostr scan` writes, byte for byte, and `roostr scan`
  writes it without one.

### F6. A command of several lines

Seen (`repro-multiline-op.sh`): `setup: |` with two lines makes `project.yml` unreadable.

- A finding on `operations.setup`: a command is one line; put a procedure of several steps
  in a script and name the script here. It does not make `project.yml` unreadable, as the
  length limits do not.
- The overview shows the first line followed by ` ...`. JSON carries the whole string.
- **Proposed**: a line break at the very end (a `|` block of one line) does not make a
  command several lines, and is not shown.

### F8. A closed stdout keeps the exit code

Seen (`repro-epipe.sh`): with 1500 processes needing attention, `roostr check --json |

### F9. A scan script that cannot be started

Seen (`repro-shebang.sh`): an executable `.roostr/scan` whose `#!` line ends in `\r`
(saved with Windows line endings) or names an interpreter that does not exist is reported
as not executable, "Cannot run .roostr/scan: No such file or directory".

- When the file is executable and cannot be started, `check` and `scan` say that its `#!`
  line names an interpreter that cannot be started, name it, and, when the line ends in
  `\r`, say that the file has Windows line endings. `scan` exits 2, as for a script that is
  not executable; for `check` it is a problem, exit 1.
- **Proposed**, JSON: a new kind, `scan_cannot_start`, with `interpreter`, the program the
  `#!` line names as written (`"/bin/sh\r"`), or `null` when there is no `#!` line. The
  remedy differs from `scan_not_executable` (`chmod +x`), so a consumer should be able to
  tell them apart, and a new kind keeps format 1 by record 5's rule.

### F10. `show` and options

Seen (`repro-show-help.sh`): `show --help`, `show -h` and `show --verbose` look the option
up as an id and exit 1; every other command exits 2.

- An option `show` does not take exits 2 and names it. `--` ends the options:
  `show -- --verbose` looks up the id `--verbose`.
- `show cancel-booking.yml` suggests `cancel-booking`. **Proposed**: so does
  `show .roostr/processes/cancel-booking.yml`, the path `validate` and `check` print, which
  is what an agent copies. The text is matched with its folders and a final `.yml` removed.

### F11. Names YAML would read as numbers

Seen (`repro-outcome-keys.sh`): outcomes named `200:` and `404:` make the record unreadable,

  `1.0` is `"1.0"`, `true` is `"true"`.
- **Proposed**: the same for operation names; every name in a map is a name, whatever YAML

## Raised

1. **F1: "the base's merge base is within the fetched history" is not enough.** A shallow
   clone cuts every line of history at the depth, side branches included. When a branch
   merged after the base is cut, the oldest of its commits in the clone lies after the base
   and looks as if it added every file, records included; the real change to `booking.rb`
   lies beyond it, so `booking.rb` looks changed together with its records and is not
   reported. Tried with the current build on Atelier: `main` at A; a branch from A changes
   `booking.rb` in the first of four commits and is merged into `waiting-list` with a merge
   commit. With full history `check --base origin/main` lists `book-workshop` and
   `cancel-booking`, exit 1. In a clone of depth 2 it prints `No problems found`, exit 0,
   though A, the merge base, is in the clone.

   Proposed rule: in a shallow clone, `check --base` runs only when every commit at the
   clone's edge (Git lists them in `.git/shallow`) that `HEAD` reaches is reached by the
   base too, so that every commit after the base is in the clone with its parents. Edges
   of branches `HEAD` does not reach do not matter. Otherwise exit 2: the history after the
   base is not all in the clone; fetch more of it, or all of it with `git fetch
   --unshallow`. `--base HEAD` in a depth-1 clone runs (its edge is `HEAD`); so does the
   usual pull request branch of a few commits cloned deep enough. Scenario 274.
