# Record 10: the project map in the agent's context at session start

Date: 2026-11-06. Changes behaviour of records 1 to 9, which all stand except where this
record says otherwise. Branch `map`, from `sessions`.

Status: accepted. Decisions 1 to 11 are the coordinator's design (`brief-map.md`), after two
research reports and two design reviews, approved by the owner. Where the brief left room,
or where this record decided differently, the draft marked it Proposed or Raised; the
coordinator accepted every one of them for the owner, and they are written below as
decided: the split character sets (the map strips the wide set, `validate` reports the
narrow one), findings named by key path, a whole JSON object read before the stdin deadline
counting, the map reading only `project.yml` and the records, an unreadable record left out
without a word, the labelled `Stack:` and `Description:` lines, and the header's wording.
**Decided in writing the tests** marks what was settled after that, while the tests were
written; each says why.

## The problem this record serves

An agent starts every session knowing nothing about the project. `.roostr/` holds what it
needs, but the agent has to think of running `roostr` first; the AGENTS.md line asks it
to, and agents often skip it. The SessionStart hook that record 9 added can put a short
map of the project into the agent's context before its first step. The evidence on
context files is mixed (shorter runs in one study, ~20% more cost and no gain in another),
and agents act on what they are shown, so the map is small, factual, and free of to-do
lists, and it is measured in A/B runs before it is called done (outside this record).

## Decided

### 1. One command, two independent jobs

`roostr session start` records the session's start as in record 9, then prints the map.
Neither job depends on the other: the map is printed when recording fails (no Git, no id,
input that is not JSON), and nothing about the map touches the record. This ends record
9's "prints nothing on stdout, ever". Record 9's one line on stderr when it cannot record
stays. There is no option to turn the map off: the hook line belongs to the project, and
`roostr session start >/dev/null` keeps the record without the map (one sentence in
FORMATS).

### 2. When

The map is printed when `source` is `startup`, `clear` or `compact`, and when it is
missing, not a string, or a word roostr does not know. On `resume` and `fork` nothing is
printed: the restored history already holds the earlier copy. The record is handled as in
record 9 for every source.

### 3. Nothing where there is no project

When no `.roostr/project.yml` is found (looked for as every command looks for it, from the
current folder up), stdout and stderr are empty and the exit is 0: the top of a monorepo, a
hook set for every repository of a user. When `project.yml` is there and the overview
cannot read it, stdout is empty, the exit is 0, and stderr has one line naming
`.roostr/project.yml` and `roostr validate`. **Decided in writing the tests:** "cannot
read" is the overview's rule (it does not parse, is not a mapping, has no `name`, has an
unknown key, or a key does not have its shape), not only "does not parse" as the draft had
it, and the draft's example of an unknown key still giving a map was wrong: the overview
refuses such a file. A `project.yml` that reads with findings (8 `watch_out` items, a note
too long) gives a map, as the overview still prints.

### 4. Output

Exactly one JSON object on one line, then a newline, and nothing else on stdout:

```
{"hookSpecificOutput":{"hookEventName":"SessionStart","additionalContext":"<the map>"}}
```

Exactly these keys, in this order. Never roostr's `"format"`. One write; a stdout closed
before it is ignored, as for every command; exit 0. JSON escapes only what JSON requires
(`"`, `\`, and the newline as `\n`); other characters, accented letters and emoji included,
are written as UTF-8. One output shape reaches the model in Claude Code, Gemini CLI and
Codex CLI alike; plain text does not reach it in Gemini CLI.

### 5. Built from `.roostr/` alone

The map reads `.roostr/project.yml` and the readable records in `.roostr/processes/`,
nothing else: not `entrypoints.tsv`, not the scan script, not Git, not commit messages, no
file outside `.roostr/`, no project code run. So it does not depend on the clock,
`COLUMNS`, a terminal, or Git being installed: the same files give the same bytes. Not
reading `entrypoints.tsv` means the map has no areas: a group is a heading only when a
process names it, and an area with no process (Atelier's `Workshops`) is not in it.

### 6. Content, in this order

```
roostr project map of Atelier, from .roostr/, kept by people and agents working here. Records can lag the code; where they differ, the code is current. `roostr show` with a process id prints a process in full: files, entrypoints, how to try it, outcomes. `roostr` prints the overview and recent changes.

Stack: Rails 8, PostgreSQL, Solid Queue
Description: Sells places on a pottery studio's workshops and reminds the people who booked.

Watch out:
- Stripe runs in test mode on staging; never use a real card there.
- The reminder job runs at 18:00 in the studio's time zone, not UTC, so a booking made later that evening for the next morning gets no reminder.

Operations:
- start: `bin/dev`
- test: `bin/rails test`

Processes by group, each as id: description [first files]:
Bookings:
- book-workshop: Reserve a place, take payment and confirm by email. [app/models/booking.rb, app/services/book_workshop.rb]
- cancel-booking: Cancel a booking and free the place for the next person on the waiting list. [app/models/booking.rb]
Notifications:
- remind-attendees: Remind attendees the day before a workshop [app/jobs/booking_reminder_job.rb]
```

That is Atelier's map, the test fixture, as `additionalContext` holds it: 1,145 bytes, 19
lines, no newline at the end (`test/expected/session_map_atelier.txt`). The JSON line
around it is 1,241 bytes. The rules:

- **The header** is one line, always first, and never shrunk or cut: the brief's wording
  with "kept by" for "written by" (the records are maintained, not written once), and a
  last sentence that says what `roostr` adds, since the map leaves out the last 7 days and
  what needs attention. 296 characters besides the name, starting with the marker
  `roostr project map`. **Decided in writing the tests:** the draft's header for a
  `project.yml` without `name` is dropped. Without `name` the overview cannot read
  `project.yml`, so there is no map (3).
- **The name** is in the header only. Then `Stack: ` and `Description: ` lines, each left
  out when the key is absent.
- **Watch out:** every item, in the file's order, `- <item>`.
- **Operations:** in the file's order, ``- <name>: `<command>` ``, followed by ` (<note>)`
  when it has a note. An operation named exactly `deploy` (init's own name) is left out;
  so is one with no command, as in the overview. A command of several lines (a finding)
  shows its first line and ` ...`, as in the overview. **Decided in writing the tests:**
  the ` ...` goes after the closing backtick (``- setup: `bin/setup` ...``), so that what
  is in backticks can be run as it is. Environments are left out.
- **Processes:** a legend line, then the groups, each as `<group>:` on its own line, then
  one line per process: `- <id>: <description> [<first file>, <second file>]`, the first
  two paths of `files` (notes left out), `[<first file>]` with one, no brackets with none.
  No wrapping, no padded columns. The legend line says how to read the lines, and changes
  with the shrunk forms (7). **Decided in writing the tests:** groups are in byte order of
  their names and processes in byte order of their ids, `other` last; FORMATS does not
  give the overview's order, so the map names its own.
- A part with nothing in it is left out, its heading too. A project with only a name and
  no readable record gives the header alone.
- A record that cannot be read (a finding) is left out of the map without a word. Saying
  so would be a to-do item; `validate`, `check` and the gates report it.
- Text is printed as written, after the character rules (8). **Decided in writing the
  tests:** the draft's "a description written over two lines" cannot reach the map:
  `name`, `stack`, `description`, `group`, a watch-out item and a note must be one-line
  strings, and a value that is not makes the record or `project.yml` unreadable. A plain
  value continued on the next line is one line once YAML has read it. What can still put
  a line break inside an item is U+2028 or U+2029, which become a space.
- Left out: entrypoints and their counts, "N described", "not scanned", LAST 7 DAYS,
  NEEDS ATTENTION and every "out of date" mark, the records' names, `try`, `outcomes`,
  `why`, `checked`, environments.

### 7. One limit: 8,000 bytes

`additionalContext`, as UTF-8 after decoding the JSON, is at most 8,000 bytes: under
Claude Code's 10,000 characters and Codex's about 10,000 bytes. A map of exactly 8,000
bytes is printed whole. Over it, the map is shrunk, deterministically, and the first form
that fits is printed:

- (a) each process as `- <id> [<first file>]`, the legend
  `Processes by group, each as id [first file]:`;
- (b) the ids alone, one line per group, `<group>: <id>, <id>, ...`, the legend
  `Process ids by group:`;
- (c) form (b), with lines removed from its end until it fits with its closing line.

Every shrunk form ends with a blank line and one closing line, counted within the limit,
that says what is left out and where to read it:

- (a) ``Left out to keep this map within 8,000 bytes: each process's description and all its files but the first. `roostr` prints the descriptions; `roostr show` with a process id prints the files.``
- (b) ``Left out to keep this map within 8,000 bytes: each process's description and files. `roostr` prints the descriptions; `roostr show` with a process id prints the files.``
- (c) ``Left out to keep this map within 8,000 bytes: each process's description and files, and the last <n> lines of this map. `roostr` prints the full overview.``

The cut in (c) is at a line boundary, from the end: the processes go first, then the
operations, then watch-out items. The header is never cut. **Decided in writing the
tests:** `<n>` counts every line removed from form (b), blank lines among them, and a blank
line that would be left last is removed too (and counted), so that the closing part is
always one blank line and the closing line.

The JSON line adds 78 bytes, and one byte for each newline, `"` and `\` (their escapes).
The limit stays on the decoded text.

### 8. Invisible and control characters

**In the map, the wide set, as a backstop:** no control character but the newline (a tab
becomes a space; a line break inside an item a space), no Unicode format character
(category Cf: zero-width characters, the bidi controls, the byte order mark, the soft
hyphen, the tag block U+E0000 to U+E007F whole), no variation selector (U+FE00 to U+FE0F,
U+E0100 to U+E01EF). The control characters are C0 (U+0000 to U+001F), DEL (U+007F) and C1
(U+0080 to U+009F). U+2028 and U+2029 are line breaks, so they become a space inside an
item rather than vanishing between two words. The changes are made before the map is
measured.

**In `validate`, the narrow set**, reported as a finding, so that `check`, the hooks and CI
refuse it. That is the real defence; the map's stripping is the backstop. The wide set
would fire on text people write on purpose: `⚠️` (U+26A0 U+FE0F), emoji joined with U+200D,
Persian and Indic words with U+200C, Hebrew and Arabic with U+200E, U+200F, U+061C, the
soft hyphen in text copied from the web, an ideographic variation selector after a CJK
character. So `validate` reports, in every string `project.yml` and the records yield once
parsed (keys and values, `try` and `why` included, escapes included, comments not):

- control characters: C0 but tab and newline, DEL, C1;
- the bidi embeddings, overrides and isolates, U+202A to U+202E and U+2066 to U+2069;
- U+200B, U+2060 to U+2064, U+206A to U+206F, U+FEFF inside a value, U+180E, U+FFF9 to
  U+FFFB, U+2028, U+2029;
- the tag block, U+E0000 to U+E007F;
- a variation selector directly after another one.

Not reported: tab, ZWNJ, ZWJ, LRM, RLM, ALM, the soft hyphen, the rest of category Cf, and a
single variation selector after a character. The map still drops them.

- The finding is on the key's path, as every finding about a YAML file is, one per
  string, naming each such character once, as `U+XXXX`, in the order they first appear:
  `.roostr/processes/refund-booking.yml: description: holds U+202E, a character that is
  invisible or changes how text shows: remove it`. **Decided in writing the tests:** with
  two or more, `holds U+202E and U+200B, characters that are invisible or change how text
  shows: remove them`. `validate --json` gives `line` null, as for every YAML finding.
- **Decided in writing the tests:** this finding leaves a record, and `project.yml`,
  readable, as a key written twice does. The overview and `show` print the text as written
  (still open, below), and the map drops the characters. Were it to make the record
  unreadable, the map's stripping would never apply to a record.
- `entrypoints.tsv` and `.roostr/scan` are not checked.

### 9. Time

stdin is read until end of input, 1 MiB, or 2 seconds after roostr started, whichever
comes first. What was read by then is used when it is one whole JSON object: a runner that
writes the input and keeps stdin open still gets its session recorded. A cut-off or partial
input is no id, and the map is still printed. `check --session` reads stdin the same way,
so a held stdin cannot hold the Stop hook either.

init's SessionStart entry gets `"timeout":10`:

```
{"hooks":{"SessionStart":[{"hooks":[{"type":"command","command":"roostr session start","timeout":10}]}],"Stop":[{"hooks":[{"type":"command","command":"roostr check --session >&2 || { [ $? -eq 1 ] && exit 2; }"}]}]}}
```

and the same key in the subfolder form of record 9.

## Still open

- `show` and the overview print records as written, invisible characters included. A
  terminal (ESC sequences) or an agent reading `roostr show` meets them; validate in the
  gates is the only defence there.
- In form (b), one group with more ids than fit is one line longer than the limit, and (c)
  drops it whole. Not expected in practice (about 350 ids fit); keeping part of the line
  would need a rule for cutting inside it.
- A name longer than about 7,500 bytes makes the header alone exceed the limit. A
  `validate` length limit on `name` would close it; not proposed here.
