## The problem this record serves

Each item is a case likely in real use, not exotic:

1. In a container, the overview showed nothing at all when Git could not be read: no `git`
   in a slim image, or Git refusing a checkout mounted from another user ("dubious
   ownership"), or a Git too old. The overview is the "know your project in ten seconds"
   command, and most of what it shows comes from the files.
2. People and agents type a fragment or a near miss of an id (`place`, `placeorder`,
   `Place-Order` for `place-order`), and `show` only says the id does not exist.
3. In the Claude Code run the agent wrote `group: Gift cards` while the scan's area was
   `GiftCards`. FORMATS.md allows a group that matches no area, so the overview showed two
   headings for one thing and nothing said why.
4. `show` on a record without `group` put one space between id and name, where every other
   heading has three.

## Decided

### 1. The overview never fails because of Git

Today, inside a Git work tree, any Git failure makes the overview exit 2 with "Cannot read
Git repository: ..." and nothing else.

- The overview prints everything it reads from the files, leaves out LAST 7 DAYS, and
  exits 0. Records that need checking are still listed under NEEDS ATTENTION.
- **Proposed**, placement and wording (the brief left them to house style): the note
  stands in NEEDS ATTENTION, where the processes would be, after the records that need
  checking. It is two lines, the second the reason, indented by four and printed whole, as
  a path or a Git message should not be wrapped:

  ```
  NEEDS ATTENTION
    .roostr/processes/cancel-booking.yml: needs checking; run roostr validate
    Git could not be read, so changes to the code are not shown:
      git was not found on the PATH
  ```

  NEEDS ATTENTION is where the eye is when the command returns (record 3), and without the
  note an empty NEEDS ATTENTION would read as "nothing needs attention": the house rule
  that absence is never shown as zero. The first line fits the 80 columns.
- The reason, the same in the overview, `changes` and `check`:
  - `git` not on the `PATH`: `git was not found on the PATH`;
  - a Git older than 2.25: that roostr needs Git 2.25 or later, and the version found;
  - otherwise what Git said: its first line in the overview, all of it in `changes` and
    `check`, so that the `safe.directory` command Git suggests survives.
- `roostr --json` in these cases: exit 0, `needs_attention: null`, everything else
  complete. Record 5 already wrote the rule in FORMATS.md generally ("`null` when ... Git
  could not be read"), so the contract does not change.
- `changes` and `check` cannot do their work without Git: exit 2 as now, with the reason
  above on stderr. `check` without `--base` outside a Git repository works as before.
- `show`, `validate`, `scan` and `init` never read Git, and already work in these cases.

How the tests fake it: roostr runs the `git` it finds on the `PATH`. "Not installed" is a
`PATH` of one folder holding `sh`, `cat`, `touch`, `basename` and `env`, and no `git`.
"Refuses" is a script answering `--version` with 2.43.0 and failing everything else with
Git's dubious-ownership message, exit 128. "Too old" is a script answering `--version` with
2.20.0 and failing everything else as an old Git fails an option it does not know, exit
129. No test pins which option roostr uses, nor whether it asks for the version first or
only after a failure.

### 2. `show` suggests ids

- `No process with id "<id>" exists.` stays the first line; a second line, `Did you mean:
  a, b?`, lists the ids that are close: at most five, alphabetical, separated by a comma
  and a space. Nothing close: the output stays as today. Exit 1 unchanged. With `--json`,
  stdout stays empty and both lines go to stderr.
- **Proposed**, what "close" is: an id is close when, with case, `-` and `_` ignored, it
  contains the text given (equal counts as containing). The brief said "ids that contain
  the given text, or match it ignoring case, `-` and `_`"; this rule holds both and also
  catches a fragment typed in another case or with the other separator (`Booking`,
  `place_ord`), with one rule to state instead of two. No edit-distance scoring.

### 3. A group that is a near miss of an area

- `validate`, and so `check` and `invalid` in JSON, reports a record's `group` that matches
  no area but equals one when case, spaces, `-` and `_` are ignored. The finding is on the
  key `group` and names the area as the scan writes it. A group that resembles no area
  stays allowed. Only when `entrypoints.tsv` exists.
- **Proposed**: the finding leaves the record readable (record 5's rule). It is about how
  the record relates to `entrypoints.tsv`, like an entrypoint that is not there, and a
  record left out of the overview over a misspelt heading would hide the very process the
  finding is about. FORMATS.md now names it among the findings that leave a record readable.
- Checked as asked: no existing fixture or test newly fails this rule. The groups used are
  `Bookings` and `Notifications` (equal to areas), and `Reports`, `Imports` and `Gift cards`
  (like no area of any fixture: `Bookings`, `Workshops`, `Notifications`).
